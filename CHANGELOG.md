# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project will follow
[Semantic Versioning](https://semver.org/spec/v2.0.0.html) from 1.0 onward. Before 1.0, minor versions may include breaking changes.

## [Unreleased]

### Changed

- Multi-store is the default on a server, as simple as a single store. `MULTI_STORE` is `true` when unset in the Docker image, `docker-compose.yml`, the server bundle templates and the installer's `.env`; a bare `node` start, `pnpm dev` and the desktop app stay single-store, and `MULTI_STORE=false` (or `shopme-install.sh install --single-store`) is the opt-out. One domain is enough: a server installed for `boutique.fr` has the admin at `https://boutique.fr/admin`, the first store's storefront on `boutique.fr` itself (recorded at setup as that store's verified primary domain) and new stores on `<handle>.boutique.fr`; `STORE_BASE_DOMAIN` and `ADMIN_HOST` default to the install domain (`AppConfig.installDomain`). On that shared host `/admin` and `/webhooks` stay the admin and every other path is the first store. An existing single-store installation is unchanged; installs made before this keep their mode.
- Certificates need no DNS API key. The installer asks for one extra record, `*.boutique.fr` A to the server, checks it (and `doctor` again later). With nginx it installs `shopme-install.sh sync-certs`, run every minute by a systemd timer (cron without systemd): it reads the hosts the app serves from the new local-only `GET /__shopme/hosts` (loopback or private address, no proxy header, bearer `HOSTS_TOKEN` from `.env`), issues each missing certificate with `certbot --nginx -d <host>` (HTTP-01, after a DNS check), reloads nginx once, takes a lock, backs off (5 minutes doubling to 6 hours, 6 hours after a rate limit), issues at most 5 per run and logs to `/var/log/shopme/sync-certs.log`. `--dns-provider` and `--manual-dns` still give one wildcard certificate. With Caddy, on-demand TLS is the default (also in `deploy/server/Caddyfile`).
- "Create a store" is always in the account menu. In single-store mode (the desktop app, or `MULTI_STORE=false`) it opens a short dialog, in English and French, that says how to turn on multiple stores (the `.env` line on a server, "available on the server version" in the desktop app) with a link to the docs.
- Docs: quick install, multi-store and install READMEs, `.env.example` describe the default, the single wildcard record and the automatic certificates.

### Security

- Account-level admin routes (`/admin/api/account`, `/admin/api/platform`, `/admin/api/auth/*` except `me`) answer only on the admin host in multi-store mode, never on a store host, so a store theme's scripts cannot call them with a session cookie. Store-scoped admin routes keep working on a store's own host.
- The admin origin check no longer lets a request with no `Origin` header and `Sec-Fetch-Site: same-site` through; only `same-origin`, `none` or no Fetch Metadata at all are accepted.
- Restoring an off-site backup stops downloading at the import limit (2 GB), checking the announced size first and counting the decrypted bytes, and removes the partial file. A store's off-site folder may not equal or start with the platform root (`platform/`, or the platform destination's own `<prefix>platform/`).

### Added

- Sign-in screens redesigned: a dark navy backdrop with a white card, logo top left and a footer (help, terms and privacy links from the platform settings, else the ShopMe docs), the same frame for login, store setup (two steps in one card, with the theme picker and the e-mail DNS step), invitation, forgotten password and "Create a store". Login is e-mail first: the e-mail, then the password. In English and French.
- Passkeys (WebAuthn, migration `0032_loud_luckman`, table `account_passkeys`): register, list and delete them in Settings > Users > Security, sign in with "Log in with a passkey" (discoverable credentials, no e-mail needed) and a "Last used" badge kept in the browser. A passkey sign-in is phishing-resistant and user-verified, so it satisfies two-step verification and the e-mail code. Bound to the admin host (`APP_URL`, or `ADMIN_HOST` in multi-store mode). See docs/install/sign-in.md.
- E-mail verification code on a new device (table `account_login_codes`): 6 digits, valid 10 minutes, single use, 5 tries, resend with a cooldown, then a signed 90 day trusted-device cookie. Only asked when the installation can deliver e-mail, so a fresh install or the desktop app can still sign in. New "Sign-in verification code" e-mail template (EN and FR).
- Forgotten password for staff: a mailed code, then a new password (offered only where e-mail can be delivered); the "Password reset code" notification.
- Settings > Users > Add users: several addresses at once, a "Secure sign-in method" switch (invited users must set up a passkey or two-step verification, enforced at sign-in; `staff_users.require_secure_login`) and a role picker. `shopmeStaffInvite` takes `requireSecureLogin`.
- Platform settings accept `helpUrl`, `termsUrl` and `privacyUrl` for the footer of the sign-in screens.

- One-command server install: `shopme-install.sh` (Debian and Ubuntu, x86_64 and arm64) with `install`, `update` (backup first, automatic rollback when the new app is not healthy), `backup`, `restore`, `status` / `doctor` (OK / WARN / FAIL with the fix, `--json`; DNS, certificate expiry, outgoing port 25, PTR, public IP, nginx test), `add-domain`, `renew` and `uninstall`. It installs Docker, uses an existing nginx with certbot (never touching other sites) or runs Caddy in the stack, generates the secrets, adds swap on request and sets up nightly database backups (14 days) and weekly file archives. Multi-store: wildcard certificates through certbot DNS plugins (Cloudflare, OVH, Gandi, DigitalOcean, Route 53) or a manual DNS challenge, per-domain certificates, on-demand TLS with Caddy. `scripts/make-server-bundle.mjs` builds the prebuilt `shopme-server-<version>-<arch>.tar.gz` (`app/`, templates in `deploy/server/`, README) and the release workflow attaches it with the script. Tests in `packages/cli/test` run the script in dry-run mode (`SHOPME_DRY_RUN=1`). Docs: `docs/install/quick-install.md` and `.fr.md`.

- Off-site backups (migration `0031_offsite_backups`, tables `backup_destinations` and `backup_runs`). Settings > Backup sends every scheduled backup to an S3-compatible bucket (Backblaze B2, Scaleway, OVHcloud, Wasabi, Cloudflare R2, Amazon S3, MinIO or custom; official AWS SDK v3 client, multipart streaming, custom endpoint and path-style option). The access secret and an optional AES-256-GCM passphrase (applied before upload, with a warning that a lost passphrase means unrecoverable backups; `scripts/decrypt-backup.mjs` decrypts without ShopMe) are encrypted and never returned. Retention keeps N daily, N weekly and N monthly backups. "Test connection" writes, reads and deletes a small object. Each upload is kept in a history (time, size, status, error) and retried with backoff (5 min, 15 min, 1 h, 4 h); a banner on Home and Settings > Backup shows when the last off-site backup failed or none is newer than 48 hours. A single-store installation also sends a `pg_dump` of the database when the binary is reachable (`PG_DUMP_PATH`). Remote backups can be listed (newest first), downloaded decrypted and restored through the regular import after a confirmation dialog. Multi-store: destination, history and folder per store, and a platform destination for the platform owner that backs up every store and the database daily. Endpoints on private or loopback addresses are refused unless `BACKUP_ALLOW_PRIVATE_ENDPOINTS=true`. REST: `/admin/api/store/backups/offsite[...]` and `/admin/api/platform/backups/offsite[...]`. Docs: [docs/install/backups.md](docs/install/backups.md).
- Bundled themes: ShopMe ships several themes, not only Aurora. A registry discovers Aurora (`packages/theme-default`) and every folder of `packages/themes/<handle>/` with a valid settings schema, and reads the name, version, author, description (`shopme_description`, optionally per language in `shopme_descriptions`) and tags (`shopme_tags`) from `theme_info`. Online Store > Themes gets a "Free ShopMe themes" gallery below the library (preview image, description, tags, "Add to theme library", "Preview" with a desktop / mobile toggle, "In your library" once added), in English and French. Adding a theme creates an unpublished theme with its origin recorded and, for a French shop, the theme's own French seed texts (`seed_defaults` of its `locales/fr.json`; a theme without any is installed as written). The first-store setup and "Create a store" offer the same cards as a starting-theme picker (Aurora selected), and the chosen theme is installed and published. Updates work for every bundled theme (`themes.origin_theme` is the theme handle; each theme has its own `changelog.json` and `checksums.json`). API: `shopmeBundledThemes(locale)`, `shopmeThemeInstallBundled(handle)` (`userErrors` code `NOT_FOUND`), `ShopmeBundledTheme.handle`; REST `GET /admin/api/bundled-themes` (setup pages) and `GET /admin/api/theme-previews/<handle>-(desktop|mobile).webp` (signed-in only). Scripts: `scripts/theme-previews.mjs` (home page previews as WebP, Aurora included), `scripts/theme-zip.mjs` (uploadable zips), `scripts/theme-checksums.mjs` now covers every bundled theme. The Docker image and the desktop app carry `packages/themes`; `THEMES_DIR` and `THEME_PREVIEWS_DIR` override the locations. No migration. Docs: `packages/themes/README.md` and section 15 of `docs/spec/theme-format.md`.
- E-mail sent from the store's own server, with no third-party account (migration `0030_email_sending`). Settings > E-mails opens on one screen: the 3 DNS lines (SPF merged with an existing record, DKIM, DMARC) with Copy buttons, a Check button with a plain-language result per line, and a test e-mail with the remote server's answer. Details hold the port 25, reverse DNS (PTR), blocklist and public IP checks, DKIM key rotation and the latest messages; Advanced options hold the SMTP relay (Brevo, Postmark, Amazon SES, Mailgun, Resend, Zoho or any server; credentials encrypted per store) and the choice of mode. Direct delivery signs with DKIM (RSA 2048, private key encrypted at rest), looks up MX hosts with the system resolver, tries the next MX on failure, retries 4xx answers 5 times over about 23 hours from the outbox table and fails 5xx answers at once; every message is kept in an outbox with status, tries, last error and Message-ID. Marketing mail (abandoned checkout) carries `List-Unsubscribe` headers and a signed unsubscribe link. A store whose domain does not pass SPF and DKIM yet, or whose sender is a free mailbox, sends from the platform address (`no-reply@` on the APP_URL host, or `STORE_BASE_DOMAIN` / `ADMIN_HOST` in multi-store mode) with its name and Reply-To, and switches to its own address once its checks pass; the platform owner authenticates that domain in the platform area. A banner on Home and Settings and a "Set up your e-mails" card and an optional last setup step point to the page. New settings `PUBLIC_IP` and `EMAIL_ALLOW_PRIVATE_HOSTS`; `SMTP_URL` stays the installation-wide fallback. See `docs/install/email.md`.

Classic `customers/*` templates and `customer` forms, the `customer` Liquid object, and Aurora templates in English and French. Checkout starts with the signed-in customer's email and default address.
- Visit tracking that respects the cookie banner and Do Not Track.

**Checkout and payments**

- One-page checkout with discount codes, gift cards, shipping zones and rates, and tax rates.
- Payments: Stripe (PaymentIntents and signed webhooks), bank transfer, and cash on delivery.
- Cart-level discounts: `/discount/:code`, discounts in `/cart.js` and every Ajax cart response, and Liquid `cart.discount_applications`.
- Automatic discounts and buy X get Y (BXGY), with combination rules; the admin discount type chooser (amount off products, buy X get Y, amount off order, free shipping) and a code or automatic method.

**Orders and customers**

- Orders: list and detail views, fulfillments with tracking, refunds, cancellation, restock, archive, and an order timeline.
- Order editing (`orderEdit*` mutations and an edit page) and returns (`returnCreate`, `returnRequest`, approval and close), with restock on close.
- Draft orders: create, edit, calculate, complete, and send an invoice link that opens a checkout or a payment-pending order.
- Abandoned checkouts: a list in the admin, optional recovery emails after 1 to 24 hours, and a recovery link that restores the cart.
- Gift cards: issue on purchase (including recipient and scheduled notifications), balance and transactions, redemption at checkout, a public gift card page, and an admin page.
- Customer records, customer data export (`/admin/api/customers/:id/export.json`), and discount management.
- Outbound webhooks: subscriptions for Shopify-style topics, JSON payloads, HMAC-SHA256 signatures with a rotatable secret, retries with backoff, and a delivery log.
- Notification templates editor (English and French) for order, shipping, refund, cancellation, draft invoice, contact, staff invitation and login alert emails, with sender settings.

**Analytics**

- Twelve reports (sales over time, orders over time, average order value, sales by product, variant and vendor, returning customer rate, top customers, discount usage, taxes, inventory snapshot, and sessions and conversion) with a date range, a comparison picker, SVG charts, and CSV export.
- `shopmeReport` in the Admin API.

**Admin API and developer tools**

- Shopify-shaped Admin GraphQL subset, with ShopMe-specific settings operations, and documentation under `docs/`.
- Clean-room specifications and developer notes under `docs/`.
- End-to-end test suite (`pnpm e2e`): a 29-step merchant and shopper journey in a real browser, run in CI.
- English and French READMEs, roadmap, coverage report, contribution guide and security policy.
